# 0. VERIFIED FINDINGS ADDENDUM (added 2026-09-10, after running the mandatory
#    Section 56/57 dataset audit — corrections to the plan below)

This addendum documents what Sections 56-57 explicitly require before any
reconstruction code is trusted: the plan below was written before the actual
dataset/DICOM metadata was inspected, and contained a path error plus several
assumptions that the real data contradicts. Do not silently work around these
— they are corrected here, with evidence, and the rest of this file is left
otherwise unmodified as the source spec.

**1. Path error (Section 4).** The project root below is written as
`/run/media/ahmad-pervaiz/New Volume/BC_detection/BC_detection_Project`. The
actual path (confirmed by the running environment) is:
```
/run/media/ahmad-pervaiz/New Volume/BC_detection_Project
```
There is no intermediate `BC_detection/` directory. Every relative reference
elsewhere in this file (`FINAL DATASET/...`) is still correct; only the
absolute project-root prefix in Section 4 was wrong.

**2. PNG ↔ DICOM mapping (Sections 7, 15) is SOLVED, not just "attempt Method
1-5".** Every PNG/JSON stem in the 7 annotated patient folders matches a
`.dcm` file of the identical stem in `TUMOR_Anonymized_DCM/` (e.g.
`aa85df1c.png` / `aa85df1c.json` / `aa85df1c.dcm` — an anonymization hash,
not a patient identifier), 1:1, with matching PNG vs. DICOM dimensions in
every case. Ran across all 1,352 JSON files / 1,100 DICOM files: **100%
VERIFIED confidence, 0 FAILED/UNCERTAIN, for all 7 patients.** Method 1
(filename relationship) alone was sufficient — Methods 2/4/5 were not
needed. See `runs/phase2_3d/audit/audit_report.json` and
`runs/phase2_3d/mapping/slice_mapping.csv` (generated by
`scripts/phase2_audit_dataset.py`). The DICOM `PatientID` tag itself is
**blank on all 1,100 files** (stripped by anonymization) — patient identity
must come from this filename join, never from the DICOM header.

**2b. De-identification policy (added after this addendum was first
written).** Every one of the 7 verified patients is referred to from here on,
and in every Phase-2 output (reports, CSVs, filenames, meshes, images,
videos), by an anonymized code `Patient_01`...`Patient_07` — never by the
real dataset folder name. The code↔real-folder mapping lives in exactly one
place, `configs/phase2_3d.yaml` (gitignored — this repo is public — used
only so scripts can locate source files on disk; see
`configs/phase2_3d.example.yaml` for the redacted template that is
committed instead), and must never be copied into a rendered output. The rest of this addendum uses codes throughout.

**3. Section 5 is incomplete: two more patients (`Patient_06`, `Patient_07`
— both in `valid/`) also have verified DICOM+PNG+JSON, contradicting the
top-level `README.md`'s "DICOM-less patients" claim (now corrected in that
file too).** The real patient list with full DICOM+PNG+JSON correspondence
is 7, not 5: `Patient_01`-`Patient_05` (train) **plus** `Patient_06`,
`Patient_07` (valid). `valid/Tumors` and every `Normal` folder genuinely have
no matching DICOM (0 stem matches) — that part of the original plan's
caution was correct.

**4. Section 18's recommended first patient is NOT the cleanest case —
changed to `Patient_05`.** DICOM series discovery
(`scripts/phase2_inspect_dicom.py`) found that **every one of the 7 patients'
annotated slices spans multiple distinct `SeriesInstanceUID`s** (2 to 7 per
patient — e.g. `Patient_01` spans 4 series of 9/91/93/89 slices, `Patient_07`
spans 7 series from 2 to 82 slices), each series fully self-contained (every
slice of a used series is annotated; no partial-series annotation).
**`Patient_05` is the only patient with exactly one series (60/60 slices)**
— the genuinely simplest case per Section 18's own criterion ("whichever
patient has the cleanest correspondence"). This is now `first_patient` in
`configs/phase2_3d.yaml`. It is still just the *first* of all 7 — Sections
18/42/59 require validating on one patient before running the pipeline on
the rest, not stopping at one.

**5. New structural finding not anticipated anywhere in this spec: a
"patient" is not one contiguous CT acquisition.** Section 39 anticipated
*ambiguity* between candidate series requiring a stop-and-report; what was
actually found is different and more specific — a patient's annotated slices
are **partitioned across several real, fully-annotated series** (different
slice thickness/spacing per series, e.g. `Patient_01` mixes a 5.0mm-thick
9-slice series with three ~0.625mm-thick series). Consequence: **Milestone 5
("Build 3D CT volume") must build one volume PER (patient, series) pair, not
one volume per patient.** Do not merge slices across series into one array
even if their SOPs share a StudyInstanceUID — confirmed distinct
`SeriesInstanceUID`, distinct spacing. This changes the intended shape of
`ct_volume.nii.gz` (Section 21) to be per-series, and the output structure in
Section 34 should nest one more level: `ground_truth/<code>/<series_index>/`.

**6. New finding: even within a single series, z-spacing is not always
uniform.** `Patient_05`'s one series has a median 0.8mm step but 3 of 59
consecutive gaps are 2.4mm/8.0mm (i.e. missing intermediate slices in the
original export); several other series across other patients show similar
gaps (see `runs/phase2_3d/audit/<code>_dicom_inspection.json`, field
`ordering_warnings`). Section 20's SimpleITK-based volume construction must
either confirm truly-uniform spacing before calling `SetSpacing` with one
scalar mm value, or explicitly resample/document the gap — do not assume
`SliceThickness` equals the true inter-slice step (verified: it frequently
does not — e.g. `SliceThickness=1.0mm` but actual `ImagePositionPatient`
z-step is `0.8mm`, consistent with overlapping reconstruction).

**7. Labelme labels (Section 12) — inspected, not assumed.** Every one of
the 1,439 polygon shapes across all 1,352 JSON files uses exactly one label,
`"Tumor"` (capital T), shape_type `"polygon"`. No other label or shape type
exists in the dataset today. `tumor_labels` in `configs/phase2_3d.yaml` is
still a configurable list (matched case-insensitively) per Section 12's
instruction not to hard-code it, but no other label needs to be invented or
handled right now.

**8. Mask validity (Section 13) — verified, no empty masks found.** Ran
`labelme_to_mask` (Section 12's parser, implemented in
`src/future_3d/labelme_io.py`) against every one of the 1,352 matched
PNG/JSON pairs: 0 empty masks, 0 invalid JSON, 0 unknown labels, 0 dimension
mismatches (`mask.shape == PNG.shape` holds everywhere; PNG dims equal DICOM
`Rows`/`Columns` everywhere too — all 512×512).

None of this removes any later milestone from this file — it only corrects
Sections 4, 5, 18, and adds the series-per-volume nuance to Section 20/21/34
before that code gets written. Everything from Milestone 5 onward in Section
50 is still pending and should proceed exactly as specified, adjusted for
the above.

# 32. PHYSICAL TUMOR MEASUREMENTS

After reconstruction is validated, implement physical measurements.

```text

```

```text

```

Convert:

```text
mm³ → cm³
```

where appropriate.

Do not report physical measurements if spacing or slice geometry is uncertain.
